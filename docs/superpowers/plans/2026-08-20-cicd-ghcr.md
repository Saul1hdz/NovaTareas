# Plan de implementación: CI/CD con GHCR y seguridad

> **Para agentes ejecutores:** SUB-SKILL OBLIGATORIA: usar
> `superpowers:subagent-driven-development` (recomendado) o
> `superpowers:executing-plans` para implementar tarea a tarea. Los pasos usan
> casillas (`- [ ]`) para seguimiento.

**Objetivo:** que producción corra exactamente la imagen que CI validó, y que el
pipeline compruebe la seguridad de la cadena de suministro antes de publicarla.

**Arquitectura:** un único workflow con tres trabajos — `calidad` (pruebas
actuales), `imagen` (construye, migra con la propia imagen, arranca, escanea con
Trivy y publica en GHCR solo desde `main`) y `seguridad` (npm audit, Gitleaks,
CodeQL) en paralelo. El despliegue al VPS lo sigue ejecutando Argus, ahora con
`docker pull` de la imagen publicada en vez de reconstruir.

**Stack:** GitHub Actions, Docker, GHCR, Trivy, Gitleaks, CodeQL, Dependabot.

**Spec:** `docs/superpowers/specs/2026-08-20-cicd-ghcr-design.md`

## Cómo se prueba un workflow

No hay tests unitarios para GitHub Actions. El ciclo de cada tarea es:

1. Editar el YAML.
2. Validar la sintaxis en local con `actionlint` vía Docker (no hace falta
   instalarlo):
   ```bash
   docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -color
   ```
3. Commit y push.
4. Observar la ejecución real: `gh run watch --exit-status`.
5. Confirmar el resultado leyendo la salida, no suponiéndolo.

`gh run watch --exit-status` devuelve código distinto de cero si el run falla,
así que sirve como puerta y no solo como espectáculo.

### Tarea 2: Trabajo de seguridad

Aditivo: no toca nada de lo que ya funciona. Si falla, falla solo.

**Ficheros:**

- [ ] **Paso 1: añadir el trabajo de seguridad al final de `ci.yml`**

```yaml
  seguridad:
    name: Cadena de suministro
    runs-on: ubuntu-latest
    timeout-minutes: 15

    # Sin `needs`: no depende de las pruebas, así que corre en paralelo y no
    # alarga el reloj del pipeline.
    permissions:
      contents: read
      security-events: write   # publicar hallazgos de CodeQL
      actions: read

    steps:
      - name: Descargar el código
        uses: actions/checkout@v7.0.1
        with:
          # Gitleaks necesita el historial completo: un secreto borrado en el
          # último commit sigue estando en los anteriores y sigue expuesto.
          fetch-depth: 0

      - name: Configurar Node.js 22
        uses: actions/setup-node@v7.0.0
        with:
          node-version: '22.23.1'
          cache: npm

      - name: Instalar dependencias
        run: npm ci

      # Umbral `high` y no `moderate` a propósito: una puerta que salta cada
      # semana por algo que no afecta acaba desactivada, y una puerta
      # desactivada no protege nada.
      - name: Auditar dependencias
        run: npm audit --audit-level=high

      # Saul1hdz es cuenta personal, no organización: no requiere licencia.
      - name: Buscar secretos en el historial
        uses: gitleaks/gitleaks-action@v3.0.0
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

      - name: Preparar CodeQL
        uses: github/codeql-action/init@v4
        with:
          languages: javascript-typescript

      - name: Analizar el código con CodeQL
        uses: github/codeql-action/analyze@v4
```

### Tarea 4: Producción consume la imagen publicada

**Reescrita durante la ejecución.** El diseño original asumía que producción se
desplegaba con `docker compose -f compose.prod.yml up -d`. La realidad, aportada
por Argus, es otra:

- `compose.server.yml`, que **solo existe en el VPS**, redeclara `build:` para
  `migrate`, `web` y `bot` usando `dockerfile: Dockerfile.server`. Cambiar solo
  `compose.prod.yml` no habría surtido efecto: Compose habría seguido
  compilando en el servidor mientras el pipeline aparentaba lo contrario.
- `Dockerfile.server` tampoco está versionado. Nació el 10 de agosto porque el
  Dockerfile del repositorio no copiaba `/app/telegram` y el bot no arrancaba.
  Upstream lo corrigió el 11 de agosto (`4013530c95f0`), así que desde entonces
  ambos ficheros son funcionalmente idénticos: solo difieren los comentarios.
- Hoy divergen otra vez, **al revés**: el commit `8026074` elimina npm y
  corepack del runtime, de modo que la imagen del repositorio es la segura y la
  que construye el VPS retiene 8 vulnerabilidades (7 HIGH + 1 CRITICAL).
- El despliegue lo ejecuta `/usr/local/sbin/novatareas-release` (helper v3), con
  puerta de release: construye una candidata aparte, **ensaya la migración
  contra un PostgreSQL descartable**, hace dump y backup, reetiqueta, migra,
  levanta y comprueba salud cinco veces, con rollback por imagen local. Es más
  robusto que el procedimiento que este plan documentaba.
- `docs/DESPLIEGUE.md` describe un procedimiento que ya nadie usa: sin el
  overlay, sin el helper, y por tanto sin límites de memoria, sin
  `no-new-privileges`, sin ensayo de migración y sin backup.

**Decisión:** retirar el override por completo en vez de parchearlo. Perdió su
razón de ser hace nueve días y hoy mantiene vulnerabilidades en producción.

**Orden obligatorio.** Quitar el override antes de que la imagen sea descargable
dejaría al servidor sin fuente de imagen:

1. Imagen publicada en GHCR **y accesible desde el VPS**.
2. Helper v4 con `pull` y verificación de digest, conservando backup, ensayo de
   migración y rollback.
3. Retirar los `build:` de `compose.server.yml` y `Dockerfile.server` con su pin.
4. Despliegue de prueba y verificación.

## Qué queda fuera del repositorio

Cuatro acciones en la interfaz de GitHub, ninguna posible desde el código.
Todas se confirman mirando, no suponiendo:

1. Activar *Dependabot alerts* y *security updates* (tarea 2, paso 6).
2. Activar *Code scanning* con CodeQL (tarea 2, paso 6).
3. Marcar el paquete `novatareas` como público (tarea 3, paso 6).
4. Comprobar en *Actions → General → Workflow permissions* que los workflows
   pueden escribir paquetes.

## Después de esto (no ahora)

Con el pipeline funcionando y verificado en NovaTareas, extraer una guía
reutilizable para llevar lo mismo a los demás proyectos: qué partes son
genéricas (higiene del workflow, las cuatro guardias, Dependabot) y cuáles hay
que adaptar por proyecto (imagen base, comprobaciones de base de datos, la forma
de desplegar). La guía se escribe **a partir de un pipeline que ya funciona**,
no a la vez: una plantilla derivada de algo verificado vale; una escrita en
paralelo repite los errores en todos los repos a la vez.
